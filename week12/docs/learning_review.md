# 12주차 실행성·학습 적합성 검토

## 검토 판단

2학년·주당 3시간 수업에서 제공 코드를 실행·관찰·일부 수정하는 중급 입문 IoT 실습으로 적절하다. 핵심 학습은 GPIO/센서 복습에서 무선 역할(AP/STA), HTTP 메서드/JSON, 원격 상태 변경으로 확장된다. 서버 전체 코드를 처음부터 작성하거나 HTTP·MQTT·DB를 한 번에 모두 구현하도록 요구하면 3시간을 초과하므로 MySQL은 선택 확장, MQTT/WebSocket은 비교 이론으로 둔다.

## 발견한 부족점과 수정

|기존 부족점|학습에 미치는 영향|수정|
|---|---|---|
|기능 단자 중심의 배선도|브레드보드 구멍을 결정하기 어려움|38핀 보드·구멍 좌표·LED 극성·저항 위치 표시|
|센서 단독 시험 없음|센서와 네트워크 장애 원인을 혼동|00_dht_check 추가|
|팀 ID를 두 군데 바꿔야 함|전송 장치와 제어 장치가 달라질 수 있음|DEVICE_ID 한 곳으로 통일|
|STA 접속 상태 로그 부족|전송 코드가 조용히 기다리면 고장으로 오인|연결·재시도·IP·센서 실패 로그 추가|
|PC 샘플과 실측 구분 절차 부족|모의 데이터로 실측 성공을 오인|서버 초기화·센서 변화·CSV 확인|
|AP → STA 전환 안내 부족|모바일이 이전 ESP32 AP에 남음|워크북2 시작 시 공유기로 전환 안내|

## 학습 부담 조절

- 필수: 센서 단독 출력, AP/STA 역할 설명, 모바일 조회, PC POST 201, LED 명령 반영.
- 선택: DB 저장, 통신 중단 후 복구, 더 엄격한 오래된 데이터 경고 UI.
- 다음 주 확장: MQTT broker, publish/subscribe, 명령 ACK와 실제 상태 피드백, 인증·TLS.

## 단순 따라하기를 넘는 확인 질문

1. 같은 열의 a6-e6가 연결되어 있는데 센서의 세 핀을 a6,b6,c6에 꽂으면 어떤 문제가 생기는가?
2. GET과 POST를 각 한 개씩 실제 URL에 대응하시오.
3. 웹 버튼의 명령 접수와 물리 LED 상태가 항상 같은가? 명령 ACK가 필요한 이유는?
4. 서버를 15초 중단했을 때 데이터가 자동 복구되는가? 본 코드의 누락 처리 한계는?
5. 센서가 고장났을 때 0°C를 전송하는 것보다 유효하지 않은 값 처리가 적절한 이유는?

## 수행평가 (20점)

|항목|배점|증거|
|---|---|---|
|정확한 배선·극성·저항|4|사진·핀 표|
|센서 단독 정상 출력|3|시리얼 3회|
|AP 모바일 조회·제어|4|모바일 화면·실물 LED|
|PC 전송·모바일 관제|5|POST 201·CSV 10행|
|원인 설명·장애 복구|4|위 질문 2개·복구 기록|

외부 접속 가능한 서비스 완성도를 평가하는 수업이 아니라, 센서→장치→HTTP→PC→모바일과 역방향 제어 경로를 설명하고 검증하는 수업으로 운영한다.
